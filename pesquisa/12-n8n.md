# 12 — n8n para agentes de IA (MCP, boas práticas, novidades)

## 0. Estado atual das versões (contexto)

- [fato] Versão estável mais recente: `n8n@2.40.7` (25/09/2026). O beta é `2.41.x` (2.41.0 saiu em 22/09/2026). A linha 1.x ainda recebe patches (`1.123.82`, 25/09/2026). — [GitHub releases](https://github.com/n8n-io/n8n/releases)
- [fato] O n8n 2.0.0 saiu em 05/12/2025. Foi uma release de "hardening": task runners ligados por padrão, Code node sem acesso a variáveis de ambiente, nós perigosos desativados e o novo modelo Save/Publish. A 1.x teria suporte de segurança/bugs por 3 meses. — [blog: Introducing n8n 2.0](https://blog.n8n.io/introducing-n8n-2-0/)
- [fato] **O n8n 3.0 está planejado para outubro de 2026.** Breaking changes anunciados: self-hosted só via Docker (acaba npm/npx); o Execute Sub-workflow perde as fontes "Local File" e "URL", o modo "Run once for each item" e a política de chamada "Any workflow"; mais de 20 nós legados saem (Function, Item Lists, Cron…); a pasta `~/.n8n/binaryData` passa a se chamar `~/.n8n/storage`. — [v3.0 Breaking changes](https://docs.n8n.io/changelog/v30-breaking-changes)
- [dedução] Com 700 workflows, vale fazer antes de outubro um inventário de nós legados (Function, Cron, Item Lists) e de sub-workflows em modo "for each item". Dá para fazer só lendo a API atual.

## 1. MCP e n8n

### 1a. O n8n como servidor MCP: "Instance-level MCP" (oficial)

- [fato] Foi lançado em beta em 18/11/2025. A v1.120 trouxe busca de workflows e leitura de detalhes, e a v1.121 trouxe a execução. O anúncio foi feito por funcionário do n8n. — [comunidade: Introducing Instance-level MCP access](https://community.n8n.io/t/introducing-instance-level-mcp-access-in-n8n-beta/223178)
- [fato] Funciona em Cloud e em self-hosted. Para ligar: Settings > Instance-level MCP > "Enable MCP access", o que exige owner ou admin. O endpoint termina em `/mcp-server/http`. — [Connect to n8n MCP server](https://docs.n8n.io/connect/connect-to-n8n-mcp-server)
- [fato] O repositório oficial `n8n-io/skills` diz que serve para "n8n instance (any plan)" com instance-level MCP ligado, a partir da versão 2.2.0. — [n8n-io/skills](https://github.com/n8n-io/skills)
- [dedução] Portanto também serve para community self-hosted. Confirmar na instância real, porque a página de conexão não cita plano.
- [fato] No self-hosted dá para desligar tudo com `N8N_DISABLED_MODULES=mcp`, que remove endpoints e UI. — [Connect](https://docs.n8n.io/connect/connect-to-n8n-mcp-server)
- [fato] A autenticação pode ser por OAuth (recomendado; há opção de cliente "CLI (Claude Code, Codex, Gemini CLI)") ou por access token pessoal ligado ao usuário. Gerar um token novo revoga o anterior. — idem
- [fato] **Permissão por cliente**: "Each connected client only has the permissions you granted it when it connected, for example reading workflows without being able to create or run them." Dá para revisar e revogar clientes em "Connected clients". — idem
- [fato] **Exposição por workflow**: só é possível habilitar MCP em workflows **publicados** que tenham trigger de webhook, form, schedule ou chat. A exceção é `search_workflows`, que vê todos os workflows visíveis ao usuário, mas "only returns previews". Existe "Auto-expose new workflows", desligado por padrão. — idem
- [fato] **Limitação**: a exposição não é por cliente. "All clients you connect … can see all workflows you've enabled for MCP access." — idem
- [fato] A lista de callback URLs do OAuth vem aberta por padrão ("By default, n8n allows any callback URL, which is less secure"). O ajuste fica em Settings > Instance-level MCP > Access > Allowed callback URLs. — idem
- [fato] A partir da 2.36.0, um proxy ou WAF precisa deixar passar os headers `MCP-Protocol-Version`, `Mcp-Method` e `Mcp-Name`. — idem
- [fato] Linha do tempo das capacidades:
  - criar e editar workflows desde a **2.13.0**;
  - `publish_workflow`/`unpublish_workflow` desde a 2.12.0;
  - acesso por projeto/pasta desde a 2.24.0;
  - UI por cliente desde a 2.33.0;
  - histórico de versões desde a 2.29.0;
  - diff entre versões desde a 2.36.0;
  - Agents (Preview) desde a 2.34.0.

  — [Connect](https://docs.n8n.io/connect/connect-to-n8n-mcp-server), [Tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference)
- [fato] Ferramentas oficiais (resumo). Fonte: [MCP server tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference).
  - **Leitura**:
    - `search_workflows`, `get_workflow_details`;
    - `search_workflow_executions`, `get_workflow_execution`;
    - `get_workflow_history`, `get_workflow_version`, `get_workflow_versions_diff`;
    - `list_credentials` (nunca devolve segredo);
    - `get_node_usage`, `get_instance_context`, `get_instance_activity`;
    - `search_projects`, `search_folders`, `list_workflow_tags`.
  - **Construção/validação**:
    - `get_workflow_sdk_reference`, `get_workflow_best_practices`;
    - `search_nodes`, `get_node_types`, `explore_node_resources`;
    - `validate_workflow`, `validate_node_config`.
  - **Teste**: `test_workflow`, que usa pin data para não chamar serviços externos e roda síncrono com timeout padrão de 5 minutos, e `prepare_workflow_pin_data` (2.15.0).
  - **Escrita/efeito colateral**:
    - `execute_workflow`, que por padrão roda **em modo produção a versão publicada**;
    - `publish_workflow`, `unpublish_workflow`;
    - criação e edição de workflows;
    - Agents: `delete_agent` é irreversível;
    - Data tables: `delete_data_table_rows` é irreversível.
- [fato] "Most MCP tools work on unpublished workflows. The exception is `execute_workflow`, which defaults to production mode." — [Connect](https://docs.n8n.io/connect/connect-to-n8n-mcp-server)
- [fato] As ferramentas de contexto da instância (`get_instance_context` etc.) dependem de uma flag (`114_instance_activity_context`) e do módulo `instance-ai`. — [Tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference)
- [dedução] Para o nosso caso, o ganho grande é editar o **rascunho** e só depois publicar. O modelo Save/Publish separa o rascunho da produção (ver §2c). Um agente pode editar e validar um rascunho, e a pessoa revisa o diff e publica. Isso pede um cliente OAuth sem permissão de publicar e executar, se a granularidade oferecida permitir (confirmar na tela de consentimento).

### 1b. MCP Server Trigger (nó): um workflow vira servidor MCP

- [fato] O nó expõe ferramentas de um workflow para clientes MCP. A autenticação pode ser None, Bearer ou Header. Tem URL de teste e de produção (a de produção só vale com o workflow publicado). O transporte é SSE ou streamable HTTP, sem stdio. Com várias réplicas de webhook, todo `/mcp*` precisa ir para uma única réplica. — [MCP Server Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger)
- [dedução] Serve para expor **ferramentas de negócio** específicas, não para administrar a instância. Não substitui o instance-level MCP.

### 1c. MCP de documentação (oficial)

- [fato] Existem dois servidores MCP de docs. Um é o GitBook, em `https://docs.n8n.io/~gitbook/mcp`, só com a documentação publicada. O outro é o Kapa.ai, em `https://n8n.mcp.kapa.ai`, que cobre docs, fórum e blog e exige login. — [connect-to-n8n-docs-mcp-server.md](https://github.com/n8n-io/n8n-docs/blob/main/docs/connect/connect-to-n8n-docs-mcp-server.md)
- [fato] A documentação também tem `llms.txt` e `llms-full.txt`, e as páginas existem em `.md`. — ([sitemap](https://docs.n8n.io/sitemap.md), mencionado nas páginas 404 do docs)
- [dedução] Para o guia, o MCP do GitBook é a opção de risco zero: só lê documentação pública.

### 1d. n8n CLI oficial (remoto) + skill oficial

- [fato] `@n8n/cli` é um cliente leve que fala com a instância pela API pública (`npx @n8n/cli workflow list`) e se autentica com API key. Comandos disponíveis:
  - `workflow`: list, get, create, update, delete, activate, deactivate…
  - `execution`: list, get, retry, stop, delete;
  - `credential`: create, delete, schema…
  - `source-control pull`, `audit`, `package` (preview);
  - `skill install`.

  Saída em `--format=json`. **Não há dry-run nem modo somente leitura.** — [n8n CLI](https://docs.n8n.io/connect/n8n-cli)
- [fato] Tem uma skill oficial para Claude Code: `n8n-cli skill install --global`. O código fica no monorepo, em `packages/@n8n/cli/skills/n8n-cli`. — [n8n CLI](https://docs.n8n.io/connect/n8n-cli), [GitHub](https://github.com/n8n-io/n8n/tree/HEAD/packages/@n8n/cli/skills/n8n-cli)

### 1f. Comunidade: `czlonkowski/n8n-mcp`

- [fato] É um servidor MCP de terceiros com documentação de 2.864 nós (836 core e 2.028 community), 2.352 templates e validação (`validate_node`, `validate_workflow`). Tem cerca de 23 mil estrelas no GitHub, licença MIT e informa suporte ao n8n 2.40.2. — [README](https://github.com/czlonkowski/n8n-mcp)

- [fato] O próprio projeto avisa: "NEVER edit your production workflows directly with AI! … Make a copy … Test in development environment first … Export backups". — idem
- [fato] Tem telemetria, que se desliga com `N8N_MCP_TELEMETRY_DISABLED`. Há também um serviço hospedado (dashboard.n8n-mcp.com, 100 chamadas/dia grátis). — idem
- [fato] Está em manutenção ativa: v2.85.0 → v2.89.0 entre 14 e 23 de setembro, com updates acompanhando o n8n 2.39 e 2.40. — [releases](https://github.com/czlonkowski/n8n-mcp/releases)

  4. A opção hospedada mandaria a chave para fora.
- [dedução] Uso seguro: apenas em modo documentação/validação (sem `N8N_API_URL`), ou com `DISABLED_TOOLS` cobrindo todas as ferramentas de escrita. Hoje o oficial já cobre boa parte (busca de nós, tipos, validação).

## 2. Boas práticas oficiais para workflows críticos

### 2a. Tratamento de erro

- [fato] Cada workflow pode apontar um **error workflow** em Workflow Settings, que "runs if an execution fails". O mesmo error workflow pode servir a vários. Ele precisa começar com **Error Trigger**. O nó **Stop And Error** força a falha e dispara o error workflow. — [Handle errors gracefully](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully.md)
- [fato] "The Error Trigger only runs when an automatic workflow errors". Não dispara em execução manual. O error workflow **não precisa ser publicado**. O payload traz `execution.id`, `execution.url`, `lastNodeExecuted` e `retryOf`. Se a falha for no trigger, não há `execution.id`/`url`. — [Error Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger/)
- [fato] Desde a 2.38 (01/09/2026), execuções de error workflow não contam na cota. — [Changelog](https://docs.n8n.io/changelog)
- [fato] Configurações do nó:
  - **Retry On Fail**: "the node reruns until it succeeds".
  - **On Error**:
    - "Stop Workflow";
    - "Continue", que "Proceeds to the next node despite the error";
    - "Continue (using error output)", que passa o erro adiante.
  - **Always Output Data**: com o aviso de possível loop infinito em IF.

  — [Work with nodes](https://docs.n8n.io/build/understand-workflows/workflow-components/work-with-nodes)
- [dedução] "Continue" sem tratar a saída de erro engole a falha: o fluxo segue e o error workflow provavelmente não dispara, porque a execução não falha. A doc aberta não diz como a execução fica marcada. Regra do guia: toda vez que usar "Continue", usar a variante "using error output", ligar essa saída a alerta/log ou a um Stop And Error, e todo workflow crítico ter error workflow configurado.

### 2b. Execuções: retenção e verificação

- [fato] Variáveis de ambiente:
  - `EXECUTIONS_DATA_SAVE_ON_ERROR`, `..._SAVE_ON_SUCCESS`, `..._SAVE_ON_PROGRESS`, `..._SAVE_MANUAL_EXECUTIONS`;
  - pruning com `EXECUTIONS_DATA_PRUNE`, `EXECUTIONS_DATA_MAX_AGE` (padrão 336 h = 14 dias) e `EXECUTIONS_DATA_PRUNE_MAX_COUNT` (padrão 10.000);
  - `EXECUTIONS_DATA_HARD_DELETE_BUFFER` (1 h).

  A recomendação oficial é "don't save unnecessary data, and enable pruning". — [Manage execution data](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/manage-execution-data.md)
- [fato] O salvamento também é configurável por workflow. Os **custom execution data** (`$execution.customData.set()`, até 10 chaves) servem para filtrar execuções e estão disponíveis em "Self-Hosted: Enterprise, registered Community". — [Customize executions data](https://docs.n8n.io/build/understand-workflows/understand-executions/customize-executions-data.md)
- [dedução] Com o teto de 10.000 execuções para uma instância com 700 workflows, o histórico de fluxos de alto volume (WhatsApp) pode cobrir só horas. "Não achei execução" não prova que o workflow não rodou. O agente deve checar a política de retenção antes de concluir.
- [fato] Como verificar se roda: `GET /api/v1/workflows?active=true` lista os publicados. `GET /api/v1/executions` aceita os filtros `workflowId`, `status` (error, success, waiting, crashed…), `startedAfter`/`startedBefore` e `includeData`. — [Pagination](https://docs.n8n.io/connect/n8n-api/pagination), [Executions API](https://docs.n8n.io/connect/n8n-api/executions)
- [dedução] Um sub-workflow chamado por outro não precisa estar "active" para receber chamadas pelo Execute Workflow (ver §2e). Então `active=false` não significa "morto": é preciso ver quem o chama (`get_node_usage` do MCP, ou buscar o ID nos JSONs).

### 2c. Versionamento

- [fato] **Save x Publish (2.0)**: o salvamento é automático ("typically within 1 to 5 seconds"), "All edits remain in draft until you publish", e "Production executions will use this published version, not your latest edits". — [Save and publish](https://docs.n8n.io/build/understand-workflows/save-and-publish-workflows.md)
- [fato] **Histórico de versões**: todos os planos veem as versões das últimas 24 h, o Cloud Pro vê 5 dias e o Enterprise vê o histórico completo. Dá para restaurar, clonar e baixar JSON. Versões nomeadas (Pro/Enterprise) nunca são podadas. Mudar configurações do workflow não cria versão. — [View change history](https://docs.n8n.io/build/manage-workflows/view-change-history.md)
- [fato] O diff visual entre versões chegou na 2.13 (16/03/2026). — [Release notes 2.x](https://docs.n8n.io/changelog/release-notes-2.x)
- [fato] **Source control / environments (git)**: disponível nos planos "Business and Enterprise". O push envia workflows, tags e *stubs* de credenciais e variáveis, sem segredos. O pull "overwrites any changes you've made if they aren't stored in Git". A doc diz que "you shouldn't view n8n's source control as full version control" (não tem PR/merge). — [Use source control](https://docs.n8n.io/administer/use-source-control-and-environments), [Use Git in n8n](https://docs.n8n.io/administer/use-source-control-and-environments/use-git-in-n8n)
- [fato] Alternativas no plano comunitário:
  - CLI do servidor: `n8n export:workflow --all --backup` (ou `--separate`, `--published`). O import mantém IDs e **sobrescreve** IDs iguais. `export:credentials --decrypted` grava segredos em texto puro. — [Use the command line](https://docs.n8n.io/deploy/host-n8n/configure-n8n/use-the-command-line)
  - **n8n packages** (`.n8np`, desde a 2.27, **Preview**): levam só stubs de credencial (ID, nome, tipo). — [n8n packages](https://docs.n8n.io/build/manage-workflows/n8n-packages)
- [dedução] No community, o equivalente barato a versionamento é um job que exporta periodicamente os JSONs via `GET /workflows` para um repositório git. O agente compara com esse snapshot antes e depois de cada mudança humana. Isso compensa a janela de 24 h do histórico.

### 2d. Credenciais

- [fato] Credenciais são "securely stored authentication information". A doc orienta usar o sistema de credenciais. — [Create and edit credentials](https://docs.n8n.io/build/understand-workflows/create-and-edit-credentials.md)
- [fato] O JSON exportado do workflow inclui nome e ID das credenciais, sem os segredos. Porém um HTTP Request importado de cURL pode trazer headers de autenticação no JSON, que devem ser removidos antes de compartilhar. — [Export and import](https://docs.n8n.io/build/manage-workflows/export-and-import)
- [fato] No queue mode, a encryption key do main precisa ser compartilhada com os workers. — [Enable queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode.md)
- [fato] A API tem `PATCH /credentials/:id` para rotação (2.4). A ferramenta MCP `list_credentials` nunca devolve segredo. — [Changelog](https://docs.n8n.io/changelog), [Tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference)
- [dedução] Um token colado em parâmetro ou expressão fica no JSON do workflow. Com isso ele vaza em qualquer leitura por API/MCP, no histórico de versões e em backups. O agente deve **sinalizar** quando encontrar esse padrão ao ler workflows.

### 2e. Sub-workflows

- [fato] O Execute Sub-workflow envia dados ao trigger "When Executed by Another Workflow", e o último nó do filho devolve o resultado. Dá para restringir quem pode chamar nas configurações. Sub-execuções não contam na cota. "If there are errors in the sub-workflow, the parent workflow can't trigger it." — [Break workflows into smaller parts](https://docs.n8n.io/build/flow-logic/break-workflows-into-smaller-parts.md)
- [fato] Há a opção "Wait for Sub-Workflow Completion" e o modo "once with all items" ou "for each item". — [Execute Sub-workflow](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executeworkflow)
- [fato] Mudança da 2.0: "The parent execution receives the result of the child execution". O guia de migração manda trocar o Start pelo Execute Workflow Trigger e ativar o workflow. — [v2.0 Breaking changes](https://docs.n8n.io/changelog/v20-breaking-changes)
- [dedução] A doc que abri não diz se o pai executa a versão **publicada** ou o **rascunho** do filho. Isso precisa ser testado na instância antes de o guia afirmar qualquer coisa. É crítico: editar o rascunho de um sub-workflow pode ou não afetar produção.

### 2f. Webhooks

- [fato] O nó Webhook tem duas URLs:
  - **Test URL**: só escuta após "Listen for Test Event" e mostra os dados no editor;
  - **Production URL**: registra ao publicar, e os dados vão para Executions.

  Autenticação Basic, Header, JWT ou None. Também oferece IP allowlist, CORS, "Ignore Bots" e "Only Run If". O payload máximo é 16 MB (`N8N_PAYLOAD_SIZE_MAX`). A resposta pode ser Immediately, When Last Node Finishes, Respond to Webhook ou Streaming. — [Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook.md)
- [fato] Verificação de assinatura em 14 triggers nativos (Slack, Asana…) desde a 2.21 (12/05/2026). — [Changelog](https://docs.n8n.io/changelog)
- [fato] Deduplicação oficial: nó **Remove Duplicates**, operação "Remove Items Processed in Previous Executions", com escopo de nó ou workflow e histórico padrão de 10.000 itens. — [Remove Duplicates](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.removeduplicates)
- [dedução] Para WhatsApp: responder "Immediately" e processar depois evita o timeout e o reenvio do provedor. Deduplicar por `message_id` via Remove Duplicates ou via tabela no Supabase com chave única. Não achei uma página oficial de "idempotência de webhook".

### 2g. API pública: o que permite e o que é perigoso

- [fato] A base é `/api/v1`, com `X-N8N-API-KEY`. Os grupos são Workflow, Execution, Credential, User, Audit, Tags, Source Control, Variables, Data Table e Projects. Não está disponível no free trial. — [API reference](https://docs.n8n.io/connect/n8n-api/api-reference)
- [fato] **Crítico:** "Non-Enterprise API keys have full access to all the account's resources and capabilities." Scopes só existem no Enterprise. A chave tem expiração configurável. — [Authentication](https://docs.n8n.io/connect/n8n-api/authentication)
- [dedução] Portanto a chave que os agentes usam "só para leitura" **não é somente leitura** tecnicamente. A leitura é só convenção. O guia precisa tratá-la como credencial de escrita total: não expor, dar expiração curta e bloquear métodos diferentes de GET num proxy ou wrapper.
- [fato] Paginação: `limit` com padrão 100 e máximo 250, e `cursor`/`nextCursor`. — [Pagination](https://docs.n8n.io/connect/n8n-api/pagination)
- [fato] Workflows:
  - `GET/POST /workflows`, `GET/PUT/DELETE /workflows/{id}`, `POST /workflows/{id}/archive`.
  - **O PUT substitui o workflow inteiro** e, se ele estiver ativo, **republica automaticamente**, a menos que se passe `publishIfActive=false`.
  - Usa `versionId` para travamento otimista.

  — [Workflow API](https://docs.n8n.io/connect/n8n-api/workflow)
- [fato] Existem specs de activate, deactivate, publish, unpublish, archive, unarchive, history, version, transfer e test runs no código. — [spec paths](https://github.com/n8n-io/n8n/tree/master/packages/cli/src/public-api/v1/handlers/workflows/spec/paths)
- [fato] Executions: `GET`, `DELETE /executions/{id}`, `POST /executions/{id}/stop`, `POST /executions/stop` (em massa), `POST /executions/{id}/retry` (com `loadWorkflow`) e `ignoreDataSizeLimit`. — [Executions API](https://docs.n8n.io/connect/n8n-api/executions)
- [dedução] Operações perigosas para listar no guia:
  - `PUT /workflows/{id}` num workflow ativo (vai direto para produção);
  - `DELETE /workflows`;
  - `POST /executions/stop` em massa;
  - `retry`, que reenvia mensagens de WhatsApp;
  - `DELETE /executions`, que apaga evidência;
  - operações de credenciais;
  - `source-control pull`, que sobrescreve.

### 2h. Escala e timeouts

- [fato] Queue mode: main + Redis + workers, Postgres recomendado. Cada worker roda 10 jobs concorrentes por padrão. O main não deve ficar no pool de webhooks. Multi-main é Enterprise. — [Enable queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode.md)
- [fato] `EXECUTIONS_TIMEOUT` tem padrão `-1` (sem timeout), e `EXECUTIONS_TIMEOUT_MAX` define o teto por workflow. No main process o timeout é "soft", aplicado depois que o nó atual termina. — [Configure workflow timeouts](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/configure-workflow-timeouts.md)

### 2i. Testes

- [fato] Pin data: "Data pinning isn't available for production workflow executions". Não funciona com saída binária. — [Pin and mock data](https://docs.n8n.io/build/work-with-data/pin-and-mock-data.md)
- [fato] A ferramenta MCP `test_workflow` testa com pin data sem chamar serviços externos, e `prepare_workflow_pin_data` gera dados de teste. — [Tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference)
- [fato] Existem **Evaluations** para workflows de IA (comparar saídas com casos de teste) e endpoints de test run na API. — [Test and improve AI workflows](https://docs.n8n.io/build/integrate-ai/test-and-improve-ai-workflows.md), [spec paths](https://github.com/n8n-io/n8n/tree/master/packages/cli/src/public-api/v1/handlers/workflows/spec/paths)
- [fato] Ambientes separados (dev/prod) oficialmente são via source control, que é Business/Enterprise. — [Use source control](https://docs.n8n.io/administer/use-source-control-and-environments)
